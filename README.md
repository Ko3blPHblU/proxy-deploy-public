# Прокси на собственном VPS

Интерактивный установщик для **mtg (Telegram), VLESS Reality с панелью 3x-ui,
Hysteria 2, NaiveProxy и VLESS XHTTP + TLS**. На первом запуске выберите нужные
сервисы; **Enter устанавливает все пять**. Общие зависимости устанавливаются
даже при выборе только одного сервиса.

Скрипт рассчитан на отдельный VPS. Он настраивает Nginx, Docker, UFW и
сертификаты Let’s Encrypt. SSH остаётся на **TCP 22**, вход по логину/паролю
и настройки sshd не меняются. Работу через конкретного оператора связи нужно
проверять с вашего устройства: успешная установка не гарантирует доступность
из любой сети.

## 1. Подготовьте VPS и домены

Нужны:

- Ubuntu 22.04/24.04/26.04 или Debian 12/13, архитектура amd64 либо arm64,
  systemd и root/sudo. Предпочтителен новый VPS без сайтов и других прокси.
- Публичный IPv4; IPv6 указывайте только при рабочей маршрутизации на VPS.
- Собственный домен и доступ к его DNS. Скрипт не регистрирует домены.
- Открытые у провайдера **TCP 22, 80, 443**, а для Hysteria — также **UDP 443**.
  HTTP-порт 80 нужен и для дальнейшего продления сертификатов.
- Доступ с VPS к пакетным репозиториям, Docker Hub/GHCR, GitHub и Let’s Encrypt.
- Для сборки NaiveProxy — минимум **800 MiB доступной RAM**, проверяемой перед
  сборкой. Практический ориентир для всех сервисов — VPS с 2 GiB RAM и запасом
  диска под Docker-образы. Сборка может занять несколько минут.

Установщик откажется автоматически мигрировать чужие сайты Nginx, занятую
инфраструктуру или старую установку `/opt/proxy`. Если Docker уже установлен,
требуется Engine не ниже 28.0.0 и Compose v2.

## 2. Скачайте репозиторий

Подключитесь к VPS по SSH. Для публичного репозитория логин GitHub и PAT не нужны:

```bash
sudo apt-get update
sudo apt-get install -y git python3 util-linux iproute2 coreutils
git clone https://github.com/Ko3blPHblU/proxy-deploy-public.git
cd proxy-deploy-public
```

Скачивайте **весь репозиторий**: Bash-скрипт использует соседние Python-модули.
Команды ниже выполняются из каталога `proxy-deploy-public`.

## 3. Выберите способ настройки DNS

### Автоматически через Cloudflare

Зона домена должна быть активна в вашем аккаунте Cloudflare. Создайте
[API Token](https://developers.cloudflare.com/fundamentals/api/get-started/create-token/)
с правами **Zone → Zone → Read** и **Zone → DNS → Edit**, ограниченный
**Include → Specific zone → ваша зона**. Global API Key не используется.

```bash
sudo bash deploy-proxy.sh --cloudflare
```

Токен вводится скрыто в терминале. Он не сохраняется в конфигурациях,
репозитории или журнале и не передаётся в аргументах команды. При следующем
запуске с `--cloudflare` его потребуется ввести снова.

Скрипт создаёт отсутствующие A/AAAA с **DNS only** (серое облако). Он сохраняет
совпадающие записи и останавливается при конфликте IP, включённом CDN,
CNAME или делегировании поддомена. Существующие записи не удаляются и не
исправляются автоматически. Перед первой записью проверяется весь набор имён.
Если API даст ошибку посередине, созданные записи останутся; повторный запуск
добавит недостающие. Затем скрипт до пяти минут ждёт подтверждения DNS
через публичный резолвер и резолвер VPS.

В одном запуске поддерживается **одна зона Cloudflare**, все имена должны быть
её поддоменами. Общий домен для шаблона может быть вложенным, например
`vps.example.com`; тогда зоной Cloudflare укажите `example.com`.

### Вручную у любого DNS-провайдера

```bash
sudo bash deploy-proxy.sh
```

Мастер покажет все необходимые имена и сделает паузу. Создайте для них A на
публичный IPv4 VPS и, при использовании IPv6, AAAA на указанный IPv6.
Удалите ошибочные старые AAAA. В Cloudflare отключите проксирование для этих
имён. После обновления DNS нажмите Enter: скрипт проверит записи до установки.

## 4. Ответьте на вопросы мастера

1. **Что установить.** `1` — mtg, `2` — 3x-ui + Reality, `3` — Hysteria 2,
   `4` — NaiveProxy, `5` — XHTTP. Enter выбирает всё; например, `3 4 5`
   устанавливает Hysteria, NaiveProxy и XHTTP. Повторяющиеся номера не создают
   дубликатов; ошибочный ввод можно исправить.
2. **Общий домен.** Введите, например, `example.com`, чтобы получить имена
   из таблицы ниже. Можно задать метку VPS, например `vps1`. Если оставить
   общий домен пустым, мастер спросит отдельный домен для каждого выбранного
   сервиса, панели и fallback-сайта. Без `--cloudflare` они могут относиться
   к разным DNS-зонам.
3. **Зона Cloudflare**, если указан `--cloudflare`. Это имя активной зоны в
   аккаунте; оно может отличаться от общего домена шаблона.
4. **Публичные IP VPS** через пробел. Они не определяются автоматически.
5. **Email для Let’s Encrypt** — при любом режиме DNS. Введите свой адрес.
   Затем — домены, если выбран ручной ввод имён.
6. Для mtg и Reality — **внешние домены маскировки**. Это реальные публичные
   HTTPS-сайты, которые не указывают на ваш VPS. Для Reality проверяются
   TLS 1.3 и HTTP/2. Два внешних имени должны различаться и не конфликтовать
   с маршрутами вашего сервера. Для них DNS-записи на VPS не создаются.
7. Для Hysteria — пароль от 16 символов либо Enter для случайного пароля.
   Остальные учётные данные генерируются автоматически.
8. Проверьте показанный список доменов. В ручном режиме настройте DNS и
   нажмите Enter; в режиме Cloudflare введите API Token.

| Назначение | Общий домен `example.com` | С меткой `vps1` |
|---|---|---|
| Fallback-сайт, всегда | `www.example.com` | `www-vps1.example.com` |
| Подключение Telegram | `tg.example.com` | `tg-vps1.example.com` |
| Панель 3x-ui | `panel.example.com` | `panel-vps1.example.com` |
| Подключение Reality | `reality.example.com` | `reality-vps1.example.com` |
| Hysteria 2 | `hy.example.com` | `hy-vps1.example.com` |
| NaiveProxy | `naive.example.com` | `naive-vps1.example.com` |
| XHTTP | `xhttp.example.com` | `xhttp-vps1.example.com` |

Создаются только имена для выбранных сервисов и обязательного fallback-сайта.
Последний — простая HTTPS-страница для соединений без известного имени SNI.
Домены вводите без `https://`, порта или пути; международные — в punycode.

## 5. Что происходит после ввода

1. Скрипт проверяет ОС, архитектуру, права и блокирует параллельный запуск.
   После мастера проверяются DNS и внешние HTTPS-цели маскировки.
2. Проверяются занятые порты и существующие конфигурации. Сохраняются состояние
   установки и резервные копии управляемых файлов.
3. Устанавливаются зависимости, Nginx, Certbot, UFW и при необходимости Docker.
   Обновление всех пакетов ОС выполняется только с `--upgrade-system`.
4. Выбранные Docker-образы загружаются и фиксируются по digest. UFW разрешает
   SSH, HTTP, HTTPS и при выборе Hysteria — UDP 443; входящие соединения
   по умолчанию запрещаются. Правила firewall в панели VPS изменяются вручную.
5. Nginx предоставляет HTTP-проверку доменов для Let’s Encrypt. Выпускаются
   сертификаты fallback-сайта, панели и Hysteria, когда они нужны.
6. Создаются выбранные основные сервисы. Для Reality настраиваются панель
   3x-ui, inbound и первый клиент с автоматически созданными ключами.
7. Nginx направляет TCP 443 по имени SNI в нужный сервис. Hysteria использует
   отдельный UDP 443. Панель и внутренние TCP-порты контейнеров доступны
   только через loopback и маршрутизацию Nginx.
8. Проверяются контейнеры, сертификаты, маршрутизация и клиентские запросы
   Reality/Hysteria. Для mtg проверяются секрет и локальный порт; полноценный
   внешний тест Telegram нужно выполнить самостоятельно.
9. Включается таймер продления сертификатов, проверяется тестовое продление
   основных сертификатов и сохраняются профили подключения.
10. Если выбраны NaiveProxy/XHTTP, они добавляются отдельным Compose-проектом.
    Выпускаются их сертификаты, собирается Caddy с модулем NaiveProxy,
    запускается отдельный Xray для XHTTP. Реальные тестовые клиенты выполняют
    HTTPS-запросы через локальный Nginx; проверяется сохранность основных
    контейнеров и настроек. Для дополнительных сертификатов устанавливается
    отдельный обработчик продления.

NaiveProxy здесь работает через HTTPS/HTTP2; QUIC не включён. XHTTP использует
TLS, HTTP/2 и режим `packet-up`, без Vision. Его конфигурация хранится отдельно
от панели 3x-ui. TCP-порты внутри VPS: mtg — 8443, панель — 2053/9444,
Reality — 10443, fallback — 9443, NaiveProxy — 11443, XHTTP — 12443.

## 6. Подключите устройства

После успешного запуска посмотрите профили только в своём терминале:

```bash
sudo cat /opt/proxy-deploy/credentials.txt
```

В этом файле собраны данные **всех установленных сервисов**, включая NaiveProxy
и XHTTP. Для импорта в Naive-клиент дополнительно создаётся машинный профиль
`/opt/proxy-deploy/extras/naive-client.json`.

Если установка сделана старой версией с двумя файлами, после обновления
репозитория объедините сохранённые данные без перезапуска сервисов:

```bash
sudo bash deploy-proxy.sh --export-credentials
sudo cat /opt/proxy-deploy/credentials.txt
```

Старый `extras/credentials.txt` удаляется после успешной записи общего файла.
Команда использует сохранённое состояние установки; вручную изменённые в панели
пароли она не считывает. Пароль панели в файле — первоначальный.

- **Telegram:** откройте выданную ссылку добавления MTProto-прокси.
- **Reality/Hysteria/XHTTP:** импортируйте соответствующую ссылку в клиент,
  поддерживающий этот протокол и транспорт.
- **XHTTP:** нужен совместимый Xray-core. Ошибка `unknown transport type: xhttp`
  означает, что выбранное ядро клиента не распознаёт транспорт; она возникает
  до подключения к VPS. Проверьте версию и ядро клиента.
- **NaiveProxy:** используйте совместимый Naive-клиент и выданный профиль.
- **3x-ui:** адрес с индивидуальным путём, логин и пароль находятся в основном
  файле. Дополнительные сервисы в этой панели не отображаются.

Проверьте открытие сайтов с ПК и телефона, отдельно через Wi-Fi и мобильную
сеть. Локальные тесты на VPS не проверяют блокировки и маршруты вашего оператора.

## 7. Повторный запуск и добавление сервисов

Получение новой версии кода само по себе не изменяет работающие контейнеры:

```bash
git pull --ff-only
sudo bash deploy-proxy.sh --check
```

| Команда | На существующей установке |
|---|---|
| `sudo bash deploy-proxy.sh` | Проверки по сохранённому состоянию |
| `sudo bash deploy-proxy.sh --check` | Те же проверки, без установки и изменения DNS |
| `sudo bash deploy-proxy.sh --export-credentials` | Пересобрать единый файл данных подключения без перезапуска сервисов |
| `sudo bash deploy-proxy.sh --cloudflare` | Только проверка/создание DNS для сохранённых доменов |
| `sudo bash deploy-proxy.sh --add=naive,xhttp` | Добавление недостающих NaiveProxy/XHTTP, DNS уже настроен |
| `sudo bash deploy-proxy.sh --add=naive,xhttp --cloudflare` | DNS и добавление этих сервисов |

Можно указать только `--add=naive` или `--add=xhttp`. На новом VPS `--add`
включает эти дополнения в выбор мастера. Все пять сервисов и без этого флага
выбраны по умолчанию.

Существующие домены, секреты, определения контейнеров и база панели сохраняются.
Добавление дополнений не запускает обновление ОС, не перенастраивает UFW и не
пересоздаёт основные сервисы. Перед/после сравниваются их конфигурации, ID,
время запуска и счётчик перезапусков. При ошибке дополнений откатываются только
их изменения; уже работающий mtg/Hysteria остаётся под управлением основного проекта.

Обычный повторный запуск не обновляет версии образов, не добавляет пропущенные
основные компоненты и не переименовывает домены. Изменение состава основных
сервисов и миграция старых установок требуют отдельной процедуры.
`--upgrade-system` разрешён только для новой установки; обновление ОС существующего
VPS выполняйте отдельно. `--check` нельзя совмещать с `--cloudflare` или `--add`.

## Если установка или соединение не работает

Скрипт показывает текущий этап, статус компонентов, путь к журналу и резервной
копии. Ошибка возвращает ненулевой код; сообщение о локальном успехе не выдаётся
за подтверждение внешней доступности. Журналы находятся в `/var/log/proxy-deploy/`.

На основном этапе предусмотрен откат конфигураций Nginx/UFW и контейнеров после
начала транзакции. Установленные пакеты, выданные сертификаты и созданные DNS-записи
сохраняются. При неполном откате выводится предупреждение. После сбоя первого
развёртывания сохранённый `state.json` переводит обычный повторный запуск в режим
проверки: **автоматического продолжения основной установки нет**. Изучите журнал
и копию; не удаляйте состояние работающего VPS для принудительной переустановки.

Если основной этап завершился, а добавление дополнений сорвалось, повторите
`--add` для нужных сервисов. Незавершённая транзакция дополнений восстанавливается
по `/opt/proxy-deploy/extras/pending.json`; удалять его вручную не нужно.

Полезные команды диагностики:

```bash
sudo bash deploy-proxy.sh --check
sudo nginx -t
sudo systemctl status nginx docker certbot.timer --no-pager
sudo ufw status verbose
sudo ss -lntup
sudo docker compose -p proxy-deploy -f /opt/proxy-deploy/compose.json ps
sudo docker compose -p proxy-deploy-extras -f /opt/proxy-deploy/extras/compose.json ps
```

Для установки только NaiveProxy/XHTTP основной Compose-файл имеет пустой список
сервисов; проверяйте дополнительный проект. Для подробностей контейнера:

```bash
sudo docker compose -p proxy-deploy -f /opt/proxy-deploy/compose.json logs --tail 80 hysteria
sudo docker compose -p proxy-deploy-extras -f /opt/proxy-deploy/extras/compose.json logs --tail 80 xhttp
```

| Симптом | Что проверить |
|---|---|
| DNS-конфликт | A/AAAA, старый IPv6, серое облако Cloudflare, совпадение зоны и имён |
| Cloudflare HTTP 403 | Права API Token, доступ к конкретной зоне, ограничения токена |
| Certbot не подтверждает домен | DNS и доступность TCP 80 извне, firewall VPS и провайдера |
| Контейнер перезапускается | Его журнал, свободную память/диск и сертификаты |
| Локально работает, с телефона — тайм-аут | Профиль/версию клиента, TCP/UDP 443, другую сеть; для Reality — SNI, ключ и short ID |
| `unknown transport type: xhttp` | Совместимость выбранного клиентского ядра с XHTTP |
| Сборка NaiveProxy остановлена | Доступную RAM, диск и доступ к источникам сборки |

## Данные и проверка проекта

Состояние VPS хранится **вне репозитория**, в `/opt/proxy-deploy`; сертификаты —
в `/etc/letsencrypt`. Конфигурации с паролями и профили имеют права 600, каталоги
состояния — 700. Не публикуйте эти файлы, резервные копии, QR-коды или необработанные
журналы. Редактор диагностики скрывает известные секреты, но произвольный внешний
вывод всё равно следует проверить перед отправкой.

`.gitignore` исключает типовые конфигурации, ключи и рабочие каталоги. Данные
`example.com`, тестовые UUID/пароли и временный CA в тестах — синтетические;
они не являются доступом к действующему серверу. Перед публикацией проверяйте
также **историю всех веток** и email в метаданных Git, а не только текущие файлы.

GitHub Actions проверяет синтаксис Bash, ShellCheck и Python-тесты. Отдельный
Linux-тест запускает реальные NaiveProxy/XHTTP и mtg/Hysteria, проверяет добавление,
повторный запуск, откат при сбое и обработчик обновления сертификатов. Cloudflare
API/DNS и выдача сертификатов в этом тесте заменены тестовыми реализациями:
он не использует ваш токен и не изменяет настоящую DNS-зону. Полный запуск
установщика на каждой заявленной ОС этим тестом не покрывается.

Локальная проверка без установки на VPS:

```bash
bash -n deploy-proxy.sh
shellcheck deploy-proxy.sh
python3 -m unittest discover -s . -p 'test_*.py' -v
```
